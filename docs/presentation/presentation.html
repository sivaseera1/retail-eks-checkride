01 · Customer Problem

Why Customer Requests Fail Today

Two operational failure modes cause recurring customer-facing outages.

Pain Point 1

Downtime During Releases

  • Old instances terminate before new instances are ready to serve traffic.
  • In-flight requests drop during abrupt shutdown without graceful draining.
  • Bad releases have no automated validation gate or rapid rollback path.
Pain Point 2

Unhealthy Instances Receive Traffic

  • Load balancers keep routing requests to degraded or initializing processes.
  • Stuck processes are not automatically detected and recycled.
  • Single-instance or unspread replicas create avoidable blast radius.
Engagement Goal: Keep healthy Pods serving throughout normal traffic, deployments, and single-instance faults—and recover quickly when a new release fails validation.

04 · Application Health & Probe Semantics

Why Startup, Readiness & Liveness Must Be Separate

Startup Probe

GET /health

periodSeconds: 5, failureThreshold: 18 (90s budget).

  • Protects slow-starting apps during initialization.
  • Liveness & readiness wait until startup succeeds.
Readiness Probe

GET /ready

periodSeconds: 5, failureThreshold: 2 (10s reaction).

  • Failure removes Pod IP from Service endpoints.
  • Does not restart the container—prevents crash loops.
Liveness Probe

GET /health

periodSeconds: 10, failureThreshold: 3 (30s).

  • Only checks process liveness, not external dependencies.
  • Restarts genuinely hung or deadlocked containers.
Implemented in Code: Setting SIMULATE_UNREADY=true or calling POST /ops/readiness?ready=false causes /ready to return HTTP 503 while /health keeps returning HTTP 200; SIMULATE_SLOW_START=true models startup initialization cleanly.

05 · Zero-Downtime Rolling Deployments

How Releases Avoid Dropping Customer Requests

Deployment Update Policy

  • replicas: 3 baseline capacity.
  • maxUnavailable: 0 guarantees all 3 healthy Pods stay up during rollout.
  • maxSurge: 1 spins up Pod #4 first and waits for /ready = 200.
  • progressDeadlineSeconds: 180 detects stalled rollouts quickly.

Graceful Connection Draining

  • When an old Pod enters Terminating, kubelet runs preStop: sleep 5 while EndpointSlices propagate removal.
  • terminationGracePeriodSeconds: 30 gives active HTTP requests time to finish cleanly before SIGKILL.
Operational Requirement: maxUnavailable: 0 + maxSurge: 1 requires spare cluster CPU/memory for the surge Pod; otherwise the rollout stays Pending rather than dropping existing Pods.

06 · Availability, Scaling & Disruption Guards

Multi-AZ Placement, HPA & PodDisruptionBudget

Topology Spread

topologySpreadConstraints across topology.kubernetes.io/zone and kubernetes.io/hostname (ScheduleAnyway) reduces single-AZ/node risk without deadlocking smaller clusters.

Horizontal Pod Autoscaler

minReplicas: 3 to maxReplicas: 8 at 70% CPU utilization. Requires Pod CPU requests (configured: 100m) and metrics-server.

PodDisruptionBudget

minAvailable: 2 protects against voluntary disruptions (node drains / upgrades) via the Eviction API.

Key Distinctions for Stakeholders: HPA scales Pods, not EC2 worker nodes (node autoscaling is Karpenter / Cluster Autoscaler). A PDB protects against voluntary evictions, not unexpected hardware/node failures.

07 · Automated CI/CD & Recovery

Why Recovery Is Pipeline-Enforced

Continuous Verification (GitHub Actions)

  • Runs pytest (9 unit tests) + npm run build before touching AWS.
  • Builds immutable Docker image tagged with 7-char commit SHA (APP_VERSION).
  • Updates EKS Deployment and runs kubectl rollout status --timeout=180s.

Automatic Rollback Gate

  • Kubernetes pauses a bad rollout, but does not auto-undo application logic errors.
  • If rollout times out or post-deploy /ready smoke test fails, the workflow runs kubectl rollout undo and waits for rollback verification.
  • revisionHistoryLimit: 5 keeps recent revisions ready for instant recovery.
